# 日记：预算死循环（两道门，两把尺子）

提交：`d563ea1`（`core/session.ts`、`core/memory-engine.ts`、`core/model-config.ts`）

## 症状

日记一篇都没写成。每轮日志都报"预算不足，原文保留"，`knowledge/state.json` 里 `diaries` 一直是 0 条。

界面显示「剩余 550 条原文 · 0 字节」，容易误读成"原文是空的"。

## 触发场景

三个开关全部成立才会走这条路：

```
memory_mode    不是 legacy
diary_enabled  true
history_enabled true
engine         可用
```

任何一条不成立，日记那条路根本不进。

## 触发原因：两道门用两把尺子

**第一道门**（`session.ts:542`）：

```
上下文 ≥ limit.tokens × compression_trigger_percent
```

本机是 200000 × 50% = **10 万 token** 才动手。

**第二道门**（`memory-engine.ts` 里的 `reserveMemoryRequest`）：

```
reserved ≤ daily_memory_tokens
```

默认 `daily_memory_tokens = 20000`。

**为什么必卡**：等第一道门打开，原文已经几百条。一次日记请求的规模：

```
reserved ≈ 8880 + 321 × 条数
```

本机实测：447 条原文要 **152532 token**，是 20000 的 **7.6 倍**。

而且原文一条都没归档，下一轮只更大。**不是偶发，是必然。**

## 换算

按本机会话实测公式 `reserved ≈ 8880 + 321 × 条数`：

| 想整理 | 需要预算 |
|---|--:|
| 34 条 | 20000（默认值，只够这个） |
| 100 条 | 40980 |
| 200 条 | 73080 |
| 450 条 | 153330 |

**只归档 1 条也要 9201 token**，也已经超 20000 的一半。

## 几个容易误判的点

**一、调 `compression_trigger_percent` 没用。** 那只管第一道门，第二道门的尺子不变。

**二、日志里 `budget` 字段打的是模型上下文（200000），看着宽裕。** 真瓶颈是 `memory_remaining`，不是这个数。

**三、「0 字节」那文案会把人带偏。** 实际 `episodes/2026-11.jsonl` 是 5,868,399 字节，user 行 205 条、assistant 行 604 条。0 是统计 bug，不是内容空。

## 复现步骤

**快速复现**（三个数一起改，缺一个不行）：

| 文件 | 字段 | 默认 → 临时 |
|---|---|---|
| `config/session.json` | `compression_trigger_percent` | 80 → **10** |
| 同上 | `compression_target_percent` | 50 → **2** |
| `knowledge/state.json` | `settings.daily_memory_tokens` | 20000 → **1000** |

**只降触发线不行**：`desired = inputTokens - target`。目标线不动，差值是负的，`desired ≈ 0`，走 `no_fitting_prefix`，跟 `budget` 不是同一个症状。

1000 是关键：一次日记请求的固定开销 8880，比 1000 大八倍多，必被拒。

**完整复现**：保持默认，聊到 447 条，撞上 `reserved` 152532 对 20000 差 7.6 倍。

## 改动

**`memory-engine.ts`**：新增 `memoryRequestBudget(id)`，暴露"今日还剩多少额度"。

**`session.ts`**：挑段落时同时满足两个条件——装得进模型上下文，**且**装得进今日剩余预算。三种结果进日志：

```
{"status":"written","sources":461,"remaining":99,"budget":200000}
{"status":"budget","reason":"日记整理预算不足，原文保留"}
{"status":"skipped",...}
```

**`model-config.ts` + 前端**：新增 `diary` 用途，日记可单独绑模型。`options(type)` 里轻量借用 chat 类型筛选（`diary` 不是模型的 type，直接筛筛不出东西）。

**`ui/context.js`**：「0 字节」改成「日记正文 0 字符」。

## 验证

修完调高预算后（本机临时设 400000），日志：

```
{"status":"written","sources":461,"remaining":99,"budget":200000}
```

`state.json` 里 `diaries` 变成 1 条，5774 字。界面显示「日记 1 篇 · 覆盖 461 条 · 剩余 101 条 · 日记正文 5,774 字符」。

## 应用注意

**默认值 20000 装不下一次完整整理。** 作者那边如果不调高，日记会一直返回 `budget`。本机实测要 15 万以上。这是最容易踩的坑。

上限是 `MAX_DAILY_MEMORY_TOKENS = 10000000`。

**归零按 UTC 日期算**（`toISOString().slice(0,10)`），不是本地时区。澳大利亚 UTC+10，本地早上 10 点才归零。

## 另一个独立问题：BOM

`memory-engine.ts` 读 state 的 `json()` 解析前没剥 BOM。用 PowerShell 的 `Out-File` / `Set-Content -Encoding utf8` 写过这个文件，就会带 BOM，`JSON.parse` 直接抛错。

修法：解析前剥 `\uFEFF`。文件本身没坏，只影响读。

BOM 和预算两处没有依赖关系，可以拆开应用。
