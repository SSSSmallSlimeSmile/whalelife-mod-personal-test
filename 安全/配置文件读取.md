# 安全：`/api/file` 挡住敏感配置

提交：`3e2605f`（`core/web.ts`，+2）

## 症状

往 `/api/file` 传相对路径，能读到 `config/config.json` 这类文件——里面明文存着各个提供商的 API key。

## 触发原因

原有的黑名单只挡了这几种：

```ts
if (!relative || segments.some((seg) => seg.startsWith(".") || seg === "node_modules"))
  return send(403, { error: "这个路径不允许打开" });
if (/\.(env|key|pem|p12)$/i.test(relative))
  return send(403, { error: "这个文件不允许打开" });
```

`config.json` 三个条件都不碰：不以点开头、不是 `node_modules`、扩展名不是 `.env` / `.key` / `.pem` / `.p12`。

## 触发场景

- 前端某个按钮拼了路径去 `/api/file` 读
- 模型自己调了这个接口（如果它有这个工具）
- 任何能发 HTTP 请求的本地程序

## 改动

在 `.env` 那条检查前面加一条：

```ts
if (/^(config|credentials?|secrets?)\.json$/i.test(segments[segments.length - 1] ?? ""))
  return send(403, { error: "sensitive config file blocked" });
```

按**文件名**判断（最后一个路径段），不管在哪一层目录，`a/b/config.json` 一样挡。

覆盖面：`config.json`、`credential.json`、`credentials.json`、`secret.json`、`secrets.json`，大小写不敏感。

## 验证

`tsc --noEmit` 退出码 0。

手工验证：`/api/file?path=config/config.json` 返回 403 `{"error":"sensitive config file blocked"}`。

## 应用注意

**这是黑名单，不是白名单。** 换个名字的文件照样能读，比如 `config.backup.json`。

**真正的边界应该在目录层**：`config/` 整个目录不该通过这个接口对外。当前只是补了一个明显的洞。

**`config.example.json` 是提交进仓库的模板**，不含真实 key，名字也不匹配那三个模式，所以不受影响——这是有意的。
