# 工具调用泄漏成正文：检测、恢复与显示对齐

> 补丁：`all-20261119.patch`（31 个文件，+2803 −111），基线 `2ee7b09`
> 也拆成 `packages/01-functional.patch` + `packages/02-frontend.patch`，按序应用
> 所有结论来自本地实测；没验的部分在第七节逐条列出

---

## 一、现象

模型本该走结构化 `tool_calls` 通道的调用，偶尔会以**纯文本**的形式出现在 `content` 正文里，形如：

```
<｜DSML｜tool_calls>
<｜DSML｜invoke name="hands_write">
<｜DSML｜parameter name="path" string="true">...</｜DSML｜parameter>
</｜DSML｜invoke>
</｜DSML｜tool_calls>
```

特征：

- 上游返回 `finish_reason: "stop"`，`tool_calls` 为空——**不是被谁降级，是模型直接当正文写出来的**
- 标记里的竖线是 U+FF5C（全角），这是 DeepSeek 原生格式，不是编码错误
- 偶发。同一会话里有时正常，有时必坏
- 出现一次之后，同一会话里越来越频繁

宿主的默认行为是把这段当普通文本：显示给用户、存进历史、下一轮再喂回上下文。用户看到一大段乱码，实际什么也没执行。

---

## 二、根因

上游已有人报告，和我们的观察一致：

- `vllm-project/vllm#48931` — 长上下文（约 95k+ tokens）时，模型偶发**省略开头包装标记** `<｜DSML｜tool_calls>`，但照常输出完整的 `<｜DSML｜invoke>…</｜DSML｜invoke>` 块。解析器只认开头包装，标记不在，整个调用块就被当正文返回，`tools_called=False`。
- `#49117` — 上游的修复 PR（orphan-invoke fallback），思路是：正文里遇到 invoke 前缀时开一个"暂存窗口"，等工具名拼完再决定当调用还是当正文。
- `#51914` — 变体：开头包装不是省略，是拼错（`tool_calls` 写成 `toolcalls`）。

**为什么会越写越多**：一旦某轮把调用写成了正文，这段坏文本就进了历史。下一轮上下文里躺着几个"调用应该长这样"的样例，模型照着学，概率上升。这不是根因，是放大器。

---

## 三、复现

### 3.1 真实触发（需要长上下文，不好控）

1. 会话上下文堆到 9 万 token 以上
2. 让模型在同一轮里"先写一段分析，再调用工具"
3. 观察 `finish_reason`：如果返回 `stop` 且 `tool_calls` 为空，但正文里出现 `<｜DSML｜invoke`，就是这个问题

### 3.2 用历史记录回放（推荐，可重复）

我们从本地执行档案里捞出 42 条真实记录（28 条真泄漏 + 14 条正常文本），直接喂给检测和救援函数，逐条比对结果。这个方法不需要复现上游行为，也不需要改配置。

回放脚本思路：

```js
import { parseLeakedCall, salvageToolCallFromText } from "./core/tool-protocol.ts";

for (const rec of records) {
  const allowed = rec.declaredTools;          // 本轮声明的工具名
  const salvaged = salvageToolCallFromText(rec.text, allowed);
  // 断言：真泄漏必须检出；正常文本必须放行；
  //       救回的调用，rest 里不能再解出第二个完整调用块
}
```

### 3.3 我们回放的结果

```
42 条记录
  检出 28     （其中真泄漏 27 条，全部检出，0 漏）
  救回 25     参数完整，rest 里残留调用块 0 条
  剥除  3     都是"我在讨论这个 bug 时引用了它的语法"，解不出工具名
  放行 14     正常文本，包括提到标记词但不构成调用块的讨论
```

## 四、修法

分三层，缺一层都不完整。

### 4.1 检测（`core/tool-protocol.ts`）

判定从"出现标记词"收紧成"能构成调用块"：

```
有闭合标签                       → 泄漏
有带 name 和参数的 invoke 块     → 泄漏
只有开头包装、没有块             → 放行（多半是在讨论）
```

这条收紧很关键。第一版只匹配 `DSML` 三个字母，结果我在讨论这个 bug 时说的话也被截断。

### 4.2 恢复（`core/session.ts`）

在"上游没给 tool_calls"的分支里，先试恢复，恢复不了才剥：

```ts
const salvaged = salvageToolCallFromText(reply.text ?? "", declared);
const salvageable = salvaged &&
  !(historyReference && typeof reply.reasoning_content !== "string");
```

第二行是保险：恢复出来的调用也要过下面那道 `reasoning_content` 检查，**如果那道检查会拒绝，就不要恢复**，否则整轮抛错，比只剥更糟。

恢复的判定比上游 PR 更严：

```
工具名必须在本轮声明的工具列表里   allowed 为空或缺省 → 不恢复
只认单个 invoke 块                两个以上 → 视为可疑，不恢复
未闭合 → 不恢复
恢复时一并吃掉左边挂着的孤立开头包装
返回 rest = 剥掉该块后的正文，存历史用
```

### 4.3 显示对齐（`core/web.ts`）

流式守卫原来一见到标记就立刻发"工具协议异常"，而此时 session 层还没决定救不救，撤不回。更糟的是它一命中就从那里吞到结尾，把后面的正常正文也吃了。

现在的行为：

```
正常回复          照常流式
疑似泄漏          先扣住不显示
  救回来了        → 结尾一句"已按调用恢复执行"
  没救回来        → 结尾"[工具协议异常] 工具调用没有真正执行"
泄漏块之后的正文章  照常放行
```

`done` 消息里多了 `protocol: clean | recovered | broken` 字段。

### 4.4 剥空保护

第一版有个坑：如果整段回复只有一个调用块、没有别的字，剥完就是空串，走到 `if (!final) throw "模型未返回最终回复"`，**把一次协议故障变成整轮聊天失败**。

现在分三种：

```
剥完还有字              → 用剩下的字
剥完是空、且确实有标记   → 给一句"上游把调用写成了正文，已拦下，没有执行，再发一次"
剥完是空、本来没标记     → 保持原样仍然抛错（真空回复该报错）
```

## 七、没验的

1. **端到端恢复没在真实坏响应上跑过。** 要自然地撞上"上游省略开头包装"，得等长上下文偶发。我们用历史记录回放代替，测的是纯函数，不是完整链路。
2. **只在 DeepSeek 系模型上观察过。** 别的 provider 有没有同样的输出形态，不知道。
3. **"讨论时引用语法"会被剥。** 3 条记录属于这种情况。字符层面和真泄漏分不开，没有为它加语义规则。
4. **`think` 标记的泄漏没管。** 我们历史里 `think` 类标记的数量比工具标记更多（142 vs 60），这次只处理了工具调用。
5. **只在一台 Windows 机器上跑过。** 没在 Linux/macOS 验证。
