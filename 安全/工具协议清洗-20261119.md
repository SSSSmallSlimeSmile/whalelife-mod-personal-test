# 工具调用退化为正文：现象、根因分析与补丁

写给上游维护者。附一份 patch，基于 `f2a097d`（你们主线当前 HEAD 的上一提交）。

里面所有数字都是实测的，凡是没有验证的我会写明「未验证」。

---

## 一、现象

工具调用没有走 `tool_calls` 通道，而是以 DeepSeek 原生的 DSML 标记形式，从**正文通道**漏了出来，出现在聊天气泡里。用户看到的是一串像这样的东西：

```
｜｜DSML｜｜tool_calls
｜｜DSML｜｜invoke name="hands_run"
｜｜DSML｜｜parameter name="command" string="true">Get-ChildItem｜｜/DSML｜｜parameter
｜｜/DSML｜｜invoke
｜｜/DSML｜｜tool_calls
```

标签结构完整闭合，参数名和类型都在。也就是说，模型**真的想调用**，参数也组好了，只是这一轮没有走结构化通道。

一个会话里连续撞了 13 次（本地时间 13:18–15:04），之后在短测试里 10 次全部正常，直到构造出接近真实条件才复现。

---

## 二、排除了什么

这几条是实测的，不是推断。

### 1. 不是中转把 tool_calls 转成了正文

直接抓原始流，出问题那一轮：

```
finish_reason   "stop"
tool_calls      无
content         正文，包含完整 DSML 块
```

**上游根本没返回 tool_calls。** 所以「中转把结构化调用降级成文本」这个猜测不成立——没有东西可降级。

### 2. 不是长上下文本身

构造了 60 轮历史的请求，工具调用一切正常。

### 3. 不是「正文后面接调用」这个形态本身

带前言再调用的请求，`content` 有 71–254 字，`tool_calls` 照样正常返回。这个形态是**合法且正常的**。

### 4. 不是特定工具或参数结构

20 多次测试里换了十几种工具，没有哪个工具必坏。

---

## 三、找到的相关因素（有证据，但不是充分条件）

### 3.1 上下文中存在大量「调用写成正文」的历史样本

出问题的会话里，从第一次泄漏到我们开始怀疑，中间又陆续坏了很多次。事后数了一下：

```
泄漏的助手消息      27 条
合计字数            20,729 字
用到的协议区块标签  ｜｜DSML｜｜
```

这些记录全部留在上下文里，每一轮都会重新发送。

**新开会话立刻正常，老会话每轮必坏。** 这个对照很干净。

我把它理解为：上下文里堆了几十个「这个位置的输出应该长这样」的样例，于是模型继续照做。**不写工具调用反而成了异类。**

这是我们的主要假设，但没有做过对照实验（比如清空历史后同样条件能否复现），所以标为**推断**，不是结论。

### 3.2 泄漏是自增强的

每一轮泄漏都会写进磁盘、成为下一轮的上下文。所以一旦开始，不清理就不会自己停。

这一点解释了我们为什么会连续坏两个小时：不是模型突然抽风，而是错的样例越积越多。

## 四、补丁做了什么

三层，互相独立，任何一层单独都能减轻问题。

### 4.1 写入侧：存进数据库前清洗

新增 `core/tool-protocol.ts`，导出：

```ts
export function scrubProtocolText(text: string): { text: string; hit: boolean }
```

识别泄漏的协议块，从正文里剥掉。位置在消息落盘之前。

### 4.2 读取侧：拼上下文时清洗历史

在 `core/session.ts` 组装消息列表的地方，对历史助手消息再清洗一次。

**磁盘上的原文不动。** 这一点是刻意的：原始记录是证据，将来要复盘、要统计、要撤回都靠它。清洗只发生在「给模型看的那一份」上。

### 4.3 界面侧：流式输出末尾设哨兵

在 `core/web.ts` 的流式 chunk 回调外面包一层 `guardStream`：

- 尾部留 64 字节缓冲，专门盯跨 chunk 的标记
- 命中时不再把后续内容推给前端
- 发一条 `done` 事件，带 `protocolBroken: true`
- 写日志：`logger.warn("工具协议异常", { session, reason: "dsml_in_content" })`

**目的是让人一眼看出「这轮坏了」，而不是看到一串乱码猜半天。**

### 4.4 附带：循环守卫的三个参数调整

`core/session.ts` 里还带了三个常量调整：`max_rounds` 30→100、新增 `max_minutes`、`danger: "safe"` 的工具跳过同参数查重。

**这三处跟协议泄漏无关**，是我们自己踩过的坑（30 轮上限误伤了正常的长任务；无参只读工具被同参查重误拦）。如果不需要，可以只取前四个文件，或者把 patch 里 `session.ts` 的这部分 hunk 单独去掉。

## 七、没做到的

老实列在这里，省得你们花时间验证。

**一、根因没有闭环。** 我们知道「历史里有泄漏样本时，新会话正常、老会话必坏」，但没有做过严格控制变量的对照实验。第三节那两条是推断。

**二、只在 DeepSeek 系（含 MiraRouter 中转）上撞到。** OpenAI 和 Gemini 没测过，不知道是不是普遍现象。DSML 是 DeepSeek 的原生格式，别的模型可能有各自的标记，`tool-protocol.ts` 现在只认这一种。

**三、清洗是「事后修补」，不是「根因修复」。** 它让污染不再扩散、让问题可见，但没有解决「模型为什么走正文通道」这个问题。真要根治，可能得在请求侧下功夫（比如抑制正文中特定 token、或者检测到历史污染后主动重建上下文）。

**四、只在一台 Windows 机器上跑过。**

## 八、我们这边的现况

打上补丁、重启之后：

- 严重的那种退化（大段正文 + 后续调用）再没出现（一次也没）
- 不过同一时段里还有别的变量（重启、会话切换），所以**不能说补丁就是原因**

新会话明天再验。

## 九、如果你们觉得方向对

有两个我拿不准的地方，想听听你们的判断：

**一、清洗该放在哪一层？** 我们现在是写入侧存原始、读取侧给清洗版。另一种做法是写入时就改写，好处是简单，坏处是丢证据。你们觉得哪种更合适？

**二、要不要主动监测？** 比如某一轮的正文里出现了协议标记，就把这条会话标记为「上下文已污染」，下一轮自动重建上下文摘要。这个成本更高，但如果泄漏是自增强的，可能比逐条清洗更有效。
