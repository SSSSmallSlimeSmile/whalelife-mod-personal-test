# 上游合并与分歧

提交：`1e8964e`（merge）、`9dded2b` 等之前

## 背景

2026-11-16 晚上游推了 8 个提交，核心是给中转返回的 `reasoning` 字段做兼容。

我们本地那份是"缺了记 warn 继续跑"，作者做到"自动探测 + 可配置映射 + 续轮验证"，更完整，于是全量合并。

## 合并了什么

上游新增：

| 东西 | 体量 | 干什么 |
|---|---|---|
| `core/reasoning-compatibility.ts` | 113 行 | 两个流分开累计、读取与回传字段可独立配置、字段名白名单 |
| `core/diagnostics.ts` | 约 500 行 | 从 trajectories 里挖思考、工具、结果 |
| 探测逻辑 | 4 步、≤4 请求、180 秒 | 自己问中转用哪个字段名 |
| models 页 UI | — | `reasoning_compatibility` 三项配置 |

## 上游的 reasoning 修法，为什么比我们细

| 做法 | 细节 |
|---|---|
| 两个流分开累计 | `reasoning_content` 和 `reasoning` 各存一份，取时标准字段优先 |
| 显式映射时只读指定字段 | 配了 `response_field` 就只读它，不猜兜底 |
| 读取与回传分开 | `request_field` 和 `response_field` 是两个独立设置，**不能靠同名推断** |
| 补空限定范围 | `fill_missing` 只对新收到的工具响应补空，绝不给历史消息编造协议数据 |
| 字段名有名单 | 不能覆盖 content、tool_calls、usage、api_key，路径最多 4 段 |

## 两处分歧

**一、`thinkingToolHistory` 的判定（我们保留了改法）**

上游仍然按模型名猜：

```ts
/^deepseek[-/]/i.test(provider.model)
```

我们本地去掉了它，改成只认 `api.deepseek.com` 或显式 `thinking.enabled`。原因：走 MiraRouter 时模型名含 `deepseek`，但那个中转不认历史里的 reasoning 字段，会误判。

**合并时特别注意**：如果采用上游版本，就会把这个修复退回旧行为。当前本地保留了我们的写法。

**二、思考段缺失时的行为（用了上游的）**

我们原来改成"记一条 warn，继续跑"；上游要求"默认拒绝执行工具"。

上游更严格也更容易排查，换成了它的。要放行只能显式开 `reasoning_compatibility.fill_missing`。本机没开。

## 合并冲突

只有两处：

| 文件 | 处理 |
|---|---|
| `core/llm.ts` | 采用上游 `ReasoningAccumulator`，保留本地 `thinkingToolHistory` |
| config.example.json | 采用上游 diagnostics 段；其余本地段保留 |

其余七个两边都动过的文件自动合并。

## 上游没有的

`core/usage-ledger.ts`、`core/receipts.ts` 在上游不存在。

账本、交付回执，从第一天起就是本地自己加的，上游从来没接受过。

## 合并后修的旧测试

合并后跑全量测试，13 个失败，其中 12 个合并前就失败。原因都不是合并造成的：

- `/api/session` 改成分页后返回对象，测试还按数组取 `.length`
- 价目核验日期写死在测试里
- `current-session` 的假 DOM 缺 `createElement`，且 `app.js` 末尾插了 `installImageZoom()` 导致字符串替换失效

这些属于让测试跟上有意做出的实现变更，不是掩盖实现 bug。

## 应用注意

**合并提交没法用 format-patch 单独导出。** 用累计补丁，或者 `git merge` 原作者那边的新提交。

**上游后续更新时，`thinkingToolHistory` 那处要重新看一眼。** 他们已经改过两次这块，容易又被规则盖回去。
