# 插件看门狗：启动慢的插件被误杀

提交：`e3b0f15`（`core/plugin-process.ts`，+3 −2）

## 症状

```
[ERROR] 插件失败 {"id":"surf","error":{"message":"插件执行无响应，已切割"}}
[ERROR] 插件失败 {"id":"surf","error":{"message":"插件已停用；未完成的外部动作结果需核对"}}
[INFO]  插件卸载 {"id":"surf"}
```

插件装了、依赖也装了，就是起不来。每次启动 5 秒左右被切。

## 触发原因：看门狗从构造函数就开始跑

`plugin-process.ts` 里两处，原文：

```ts

this.watchdog = setInterval(() => {
  if (!this.closing && Date.now() - this.lastPulse > this.options.heartbeatTimeoutMs)
    this.fault(Error("插件执行无响应，已切割"));
}, Math.min(250, heartbeatTimeoutMs / 2));
```

```ts

  const deadline = new Promise((_, reject) => {
    timer = setTimeout(() => { ... Error("插件初始化超时，已切割") }, this.options.startupTimeoutMs);
```

**watchdog 从构造那一刻就在跑，不管 worker 有没有 ready。** `ready` 收到之前 `lastPulse` 一直停在构造时那个值。

时序：

```
0.0s   fork 进程
0.0s   watchdog 开始（heartbeatTimeoutMs = 5000）
0.0s   surf 开始 import cheerio
5.0s   watchdog 判定"执行无响应"  ← 先叫这个
15.0s  startupTimeoutMs 那道才轮到   ← 永远轮不到
```

**这是宿主的缺口，不是插件的错。** 任何启动超过 5 秒的插件都会被同样切掉——那套 `startupTimeoutMs: 15000` 现在是死参数。

## 触发场景

- 插件依赖重（`cheerio`、`sharp` 这类），import 慢
- 插件在顶层 await 里联网
- 机器慢、磁盘慢（`node_modules` 在机械盘上）

**不是插件代码有 bug。** 排查时看日志：插件加载没有任何输出就被"执行无响应"，八成是这个。

## 改动

三处，都在 `plugin-process.ts`：

```ts
26: private started = false;

47: if (message.type === "ready") { this.lastPulse = Date.now(); this.started = true; prepared(); }

56: this.watchdog = setInterval(() => {
      if (!this.closing && this.started && Date.now() - this.lastPulse > this.options.heartbeatTimeoutMs)
        this.fault(...);
    }, ...);
```

修复后分工：

| 阶段 | 谁负责 | 时限 |
|---|---|---|
| fork → ready | `startupTimeoutMs` | 15 秒 |
| ready 之后 | `heartbeatTimeoutMs` | 5 秒（不变） |

worker 卡在 import 里永远 ready 不了，15 秒那道兜住，不会漏。

## 复现步骤

1. 装一个 import 需要 5 秒以上的插件（或者给现有插件加一句 `await sleep(6000)` 在顶层）
2. 启动
3. 观察日志：修复前 5 秒被切，修复后能起来

本机实例：`plugins/surf`，`import cheerio` 约 5.15 秒，必被切。

## 验证

本机修完重启：

```
18:52:58 [INFO] 插件加载 {"id":"surf"}
```

之后无失败、停用、卸载记录。

## 影响面

26 个插件都走这份代码。实际只影响"启动中卡死"这一种情况——原本 5 秒切，现在最多 15 秒才知道。运行期的灵敏度没变。

## 备选方案（没采用）

把 `heartbeatTimeoutMs` 从 5000 调大到 15000，一行配置。

不采用的理由：那是把两件事的时间拉平来掩盖，运行期真卡死也要 15 秒才发现。修逻辑错位更干净。
