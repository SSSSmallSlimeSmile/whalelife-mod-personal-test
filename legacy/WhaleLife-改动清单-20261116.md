## 一、框架：接口与上传

这一类的共同点——不是「我想加个东西」，而是**主干在某个方向上缺一条通道**，谁也绕不过去。

### 1. 网页端不能发图片

现象：网页对话输入框只能打字，图片粘贴、拖拽一律丢失。

根因，三层都缺入口：

- `core/ui/app.js` 输入区只有一个 textarea，`sendMessage()` 只读文本
- WebSocket 帧只发 `{session, expectedSession, text, persona}` 四个字段，`maxPayload` 65536，一张截图都塞不进去
- 服务端 `/api/media` 只接受 GET，只用来读文件，没有上传口

讽刺的地方：**多模态能力本身早就有了。** `tool-content.ts` 里工具回传的图片，`image_url` 和 data URI 都支持。缺的只是「人」这一侧的入口。

改动：

- 前端：加图片按钮，支持粘贴与拖拽；待发区显示缩略图，可单张移除；超过 4 张、格式不对、解码失败都有明确提示
- 服务端：`maxPayload` 提到 32MiB；新增 `saveUploads()`，复用 `toolContentSnapshot()` 校验文件头与 MIME 是否一致，写到 `memory/uploads/<会话>/时间戳-n.<ext>`，再把路径以 `[[img:...]]` 标记追加进文本；限制 4 张 / 单张 4MiB / 合计 16MiB

**建议**：多模态入站应当做进主干，不该让每个通道各自实现一遍。

### 2. 微信截图粘贴报「无法解码」

现象：Ctrl+V 微信截图，前端报「图片无法解码」，普通截图工具复制的正常。

根因：微信截图放进剪贴板的格式是 `System.Drawing.Bitmap` / `DeviceIndependentBitmap` / `Format17` 这一堆，**没有 PNG**。浏览器拿不到现成 PNG，只能自己把 DIB 合成一张并标成 `image/png`，合成出的字节解码失败。

改动（`core/ui/app.js`）：

- 解码三层降级：`createImageBitmap` → `<img>` → 嗅到裸 DIB 就补 14 字节文件头转 BMP 再试
- 修补出来的图一律走 canvas 重编码成 PNG，画之前铺白底（32 位 DIB 的 alpha 常全为 0，不铺底会得到全透明）
- 失败提示带上拿到的 MIME 与字节数，不只四个字

补充（`core/clipboard-image.ps1` + `POST /api/clipboard-image`）：浏览器解不开时回退到系统取图——GDI+ 直接读剪贴板位图，存 PNG 传回，绕开 DIB 合成这一环。

**建议**：粘贴入口别信 `file.type`，按魔数嗅探；失败信息要给得出「拿到了什么」。

### 3. 会话历史只回最后 100 行

现象：往上翻看不到早先的对话。

根因：`/api/session` 取 `slice(-100)`，前端再滤掉工具行。一个长会话 325 行里 254 行是工具调用，最后 100 行只剩 12 条消息。

改动：先筛 `type === "message"` 再截，上限放 300；后续加了 `limit` / `before` / `tail` 三个参数支持分页。

**建议**：五处 `slice(0, N)` 的截断都该与渲染层分开——服务端截的是「给多少」，前端决定「显示多少」，两者混在一起就会出这种减法。

### 4. 中途插话不能并入当前回合，只能排队

现象：一轮还在跑时再发一句，只能等它跑完。

根因，这套骨架其实**主干里已经有**：

- `TurnInput` 能收中途追加的话，`session.ts` 在发请求前、执行工具前都会取出来，拼进「本轮用户补充」
- 但这条路只有 AstrBot 类渠道走（通过 `ChannelTurn.append`）；**网页走的是 `chat()`，第 10 个参数写死 `undefined`**

改动：

- `session.ts` 的 `chat()` 多收一个 input 参数，`channels.web()` 一路传到 `runChat`
- `web.ts` 给运行中的会话挂 inbox；带 `append: true` 的消息不进 busy 判断，直接并入，回 `{type:"append", status}`
- 前端忙碌时发送键不再禁用，改叫「补充」；那句以斜体虚线小气泡显示，服务端确认后才提示「已并入本轮」

**边界（重要）**：插话**不会打断正在执行的工具**。那句话要等手上这批工具跑完、下一次请求模型之前才进上下文。真打断得 abort，那半截结果就废了。回合刚好收尾时 append 会回 `closed`，前端提示「再发一次」。

**建议**：这个能力应该对所有通道一视同仁，现在只有一路接了。

### 5. 图片体积没有兜底

根因：链路上三个数字各管各的——单张 4MiB、合计 8MiB、`maxPayload` 32MiB，没有任何「本轮合计过大」的降级或拒绝。

改动：

- 本轮合计超 8MiB → 整批 `detail` 从 `auto` 降到 `low`
- 超 16MiB → 直接拒，报「本轮图片合计 X MiB，超过 16MiB 上限」
- 上传合计上限同步提到 16MiB（否则降级那条线永远够不着，是死代码）

**遗留**：工具回传的图片走 `tool-content.ts`，自带 16 张 / 16MiB 的账，与用户上传各算各的。合并成一本预算要另做。

**建议**：凡是拿 `JSON.stringify(messages)` 估算 token 的地方，都该配一个 `promptText()` 式的降级版本——base64 会把预算直接撑成负数，触发无谓压缩甚至拒答。

## 二、界面：对话页的两处体验

这一类是口味问题，作者不一定愿意收，我们列出来供参考。

### 1. 图片在气泡里按原始尺寸铺开

根因：`.msg-media` 只管了一部分图；markdown 里的图、工具回传的图走别的渲染路径，类名对不上，直接按原始尺寸铺满对话区。

改动：统一约束 320×220、超出裁切、指针变放大镜，点击开全屏遮罩看原图，Esc 或再点关闭。

### 2. 左侧摘要栏（迭代了七轮，最终形态）

中间走过的弯路值得说，因为它们是同一类错误的重复：

- 第一版：固定 200px 分栏 → 挤窄对话区，盖住消息
- 第二版：22px 窄条，悬停展开 → 覆盖时点不到，位置跳
- 第三版：18px 刻度 + 悬浮卡，照 ChatGPT 那版做 → 基本可用，但下面这条

**「两条紫线 / 高亮永远停在最后一格」——同一类根因，犯了三次**

1. 旧写法用 `box.scrollTop + 消息的 rect` 算位置，**假定滚动一定发生在 `.messages` 上**。实际滚动落到外层，`scrollTop` 恒为 0，而 rect 照动，于是「全都不超阈值」，每一节都判成已过，高亮永远落最后一格
2. 隐藏状态下 `getBoundingClientRect()` **全部返回 0**，不是「未知」。判定规则是「top 不超过阈值的最后一个」，0 全部命中，又落最后一格
3. `ResizeObserver` 只 `observe()` 一次，`render()` 一跑 `#messages` 整体替换，观察者盯着已经摘下来的旧节点，**从此不再触发**。尺寸没变、滚动没变，`resize` / `scroll` 也一个不来，算错的那一下就一直留着

改法：

- 只拿消息相对视口的位置比，不掺 `scrollTop`
- 开头尺寸守卫：`document.hidden` 或容器 `clientHeight < 1` 就直接返回，宁可留着上一轮，不用零尺寸算出必然错的答案
- 逐条判定时跳过已脱离文档的、宽高皆 0 的节点
- `ResizeObserver` 与 `scroll` 监听都改成「每次核对当前节点，换了就解绑再绑」
- 补 `window.focus` 与 `visibilitychange` 两个触发点

另一处：`focus` 事件原来直接调 `syncView()`，那会重新取会话、丢掉已翻出的历史、把滚动条按到底。改成 `refreshOnFocus()`，只刷状态与轨道，不碰消息列表。

**最后按需求改成等距刻度**。这里有个取舍要写明：等距之后，刻度位置只表示「第几节」，**不再等于滚动实况**。紫线仍按消息真实位置判，任何时刻只有一格。刻度多到挤不下时整体压短，最小间距 6px。

### 3. 左侧刻度点不动、翻页跳位

`#messages` 每次 `render()` 都被 `innerHTML` 整体替换。`railWatched` 守卫让滚动监听只绑一次，绑的是最早那个节点，之后所有滚动手势与刻度点击都送不到轨道。

**建议**：这是同一个教训的第三次——**「只绑一次」的守卫、只 observe 一次的观察者，在会重建 DOM 的渲染方式下都是定时炸弹。**

### 4. 分页加载

滑到顶上自动往前翻一页，用占位撑住高度，加载完恢复滚动位置。向上翻只认页面，不认 WebSocket：新消息推进来不会顶掉正在看的位置。

## 三、功能新增：模型分级路由

这一类不是修 bug，是我们缺一件东西：**按问题的难易自动挑模型**。

### 做了什么

新增 `core/model-router.ts`（351 行），四个接线点：

- `index.ts`：建实例、放进服务
- `session.ts`：`persona()` 之后、真发请求之前换 provider（`transient` 回合不路由）
- `config.json` / `config.example.json`：新增 `model_router` 段

逻辑四层：规则预判 → 决策缓存 → 判官 → 预算。档位按使用者的要求定：闲聊走 cheapest，低级思考走中档，高级 20% 概率放行到强模型，拿不准落中档。连续闲聊沿用上一档、不叫判官。

### 为什么只能落主干

**这不是工作量问题，是入口问题。** `plugin-events.ts` 写得很清楚：「Notifications run after their source operation」。插件系统只通知、不拦截，拿不到「回合开始前」那一刀；也没有模型选择相关的钩子。

现有的模型解析在 `session.ts:101`，每轮 `persona()` → `resolveChatModel()`，优先 `personas[id].model`，否则 `model_bindings.chat`。一个回合从头到尾一个模型，中途换不了。

### 一个从原插件搬过来又修掉的毛病

原插件（`astrbot_plugin_judge` 的魔改版）的规则预判里，「今天」这类日常词排在强关键词**之前**直接命中，所以：

> 「今天帮我把桌面上那个 bat 改一下」→ 判成闲聊

改法两层：日常词要同时满足「短句」且「句内无强词、无弱复杂词」才算闲聊。只加长度门槛不够——上面那句 18 字，卡在 20 字门槛里还是会误判。

**建议**：规则预判里这类高频日常词，必须做长度与共现约束，否则就是个把活判成闲聊的漏斗。

### 代价（必须说清）

判官每叫一次要等一次模型往返（我们实测 1.6 秒）。规则命中的（闲聊、短问）不叫判官，日常影响不大；但「有点内容又没关键词」的句子会明显慢半拍。

## 六、给作者的建议，按成本从低到高

1. **网页界面加一个插槽 / 渲染回调**（哪怕只是「消息渲染前」），或者允许插件声明 `ui/` 资源并自动并进 `core/web.ts:64` 的 `assets` 白名单。现在这两样都没有，所以轨道、缩略图、图片按钮这些**全部只能作为主干补丁**，插件化不了
2. **多模态入站做进主干**，不要让每个通道各自实现
3. **凡是「只绑一次」的守卫、只 observe 一次的观察者**，在会重建 DOM 的渲染方式下都要改成「每次核对当前节点」
4. **配置热加载 / 重启入口**：前端没有任何重启方式，桌面脚本又因为进程提权而失败。建议给启动 bat 加 `--force` 跳过端口探测；主干加 `POST /api/restart`，先回 202 再延迟自杀，新进程要 detached；UI 上至少提示「配置已变更、需重启」，这条比按钮有用
5. **`promptText()` 式的降级估算**，凡是拿 `JSON.stringify(messages)` 算 token 的地方都该配一份
