# 交付回执：程序验证，服务端判状态

提交：`d1e0ed8`（v1，`/deliver` 模式）、`0d7ad22`（改为默认写入回执，删掉 v1）

## 为什么做

模型会说"改好了，13039 字节"，实际文件没动，或者字节数是编的。

这类错误在文字层抓不住：模型写的话和工具返回的原文，在上下文里长得一模一样，没有哪一行标着"这句是程序说的"。

所以要在**服务端**留证据。

## 核心设计

**一、写入后回读**

写文件类工具落盘后，再 `readFile` 一遍、`stat` 量字节、算 sha256。回读状态三选一：`ok` / `mismatch` / `failed`。

回读整段用 `try/catch` 包住，读失败记 `readback: "failed"`，**不让它把写入本身判成失败**。

**二、按任务归属**

开工时采集基线：HEAD、`git status --porcelain`、每个目标的路径 / 存在性 / SHA-256。

收尾时对照：目标变了只说明内容变了，要算本次交付，还必须有**属于本次任务、路径对得上的写入或提交回执**。并发改动、别的提交不能蹭。

**三、状态只由程序写**

六档：`交付未登记` / `未执行` / `未验证` / `失败` / `部分完成` / `已完成`。

模型只能解释状态，不能覆盖。

**四、前端区分两种气泡**

模型说的话是普通气泡；程序回执是另一条窄条，灰底带图标，写「2 个文件 · 校验通过」或「1 个文件 · 回读失败」。

## 为什么 v1 被推翻

v1 是 `/deliver` 模式：用户要显式进这个模式，还得提前说清路径。

`0d7ad22` 的理由：成本太高，而"零执行也敢报完成"这件事**不需要知道目标就能拦**——没有回执就是没有回执，管你要交什么。

所以 v1 整个删掉（`core/delivery.ts` 273 行、`tests/delivery.test.ts` 167 行），换成默认写入回执（`core/receipts.ts` 85 行）。

## 触发场景

- 模型写了文件并声称成功
- 模型跑了一个命令，声称测试通过
- 模型说"改好了"但这一轮零工具调用

前两种有回执可比；第三种只能判「未执行」。

## 复现步骤

**回读正常**：

1. 让模型写一个文件
2. 看工具返回里有没有 `回执：path（N 字节，sha256 前 12 位 …）`
3. 对照 `Get-Item` 的字节数

**回读失败**：

把写入路径改成一个只读目录，或者写完后立刻删掉文件，看是否返回 `回读失败：原因`。

**验收表**（原九条 + 一条）：

1. 写文件后有回读字节
2. sha256 可比对
3. 补丁类要记 `git apply --check` 的退出码
4. `git` 类要单独记 git 自己的退出码（防 PowerShell 外层 0 掩盖）
5. 无工具调用却有交付声明 → 状态「未执行」
6. 程序发结论，不由模型发
7. 实时界面、最终消息、刷新后重载三处状态一致
8. 回执摘要带任务 ID 进上下文，明细留档案
9. 失败也留档：「工具已执行，回读失败：文件不存在」
10. 模拟模型在第一个分片就吐"写好了，7877 字节"、整轮不调工具 → 实时界面和重载后都不出现这句

## 已知短板

**只管文件交付这一类。**

"测试通过 695 条""命令退出码 0"这些编的数字还拦不住——它们没有对应的回执结构。

**聊天里贴的"工具返回原文"不算凭证。** 模型可以手抄一段看起来像原文的东西，用户分不清。能作证的只有程序登记过的那份。

**流式那层没做。** 模型文字仍然逐字推前端，核验完成前假结论已经在屏幕上了。前辈的答复里这条是要求进第一版的，我们的实现还差一层"扣住成文、收尾后发"。
