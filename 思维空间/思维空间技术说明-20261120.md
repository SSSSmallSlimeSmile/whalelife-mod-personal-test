# 思维空间：把一串工具调用存成一次调用

这是一份给作者看的说明。插件本体在 `thinking-space/` 目录里，这份文档讲**为什么这么做、实测什么样、哪些地方想请你定**。

---

## 一、它解决什么问题

现在模型调工具是"一轮一次"：

```
第 1 轮  input 22,525   推理 46 秒   调 surf_search
第 2 轮  input 23,226   推理 44 秒   调 surf_read
第 3 轮  input 25,518   推理  9 秒   出结论
────────────────────────────────────
         input 71,269   共 99.6 秒   3 次请求
```

中间那两轮推理，做的其实是同一件事："下一步调什么"。这件事可以提前定好。

思维空间就是这个：**把一串固定的工具调用存成一个"技能"，一次 `space_run` 跑完整条链，只把最终结果带回上下文。**

```
第 1 轮  input 22,609   推理 7.4 秒   调 space_run（内部跑完 search + read）
第 2 轮  input 25,518   推理 9.4 秒   出结论
────────────────────────────────────
         input 48,127   共 17.7 秒   2 次请求
```

同一件事，**token −32%，时间 −82%**。（数据来自 2026-11-20 群聊里的两次真实运行，不是控制条件的 A/B，下面是它的局限。）

---

## 二、反面：省下的会赔回去

同一天我试过另一次，**比原生还慢还费**：

```
实测 4 轮 94,714 token   比原生 71,269 多 33%
```

原因很简单：我把参数名写成了 `query`（工具 schema 里的名字），而技能声明的是「关键词」。校验器当场拦住，多废一轮。

**这是这类设计真实的代价：它把"每一步要想什么"提前固化了，写错就是写错，不会自己纠正。** 原生模式里模型下一轮看见报错能自己改；技能组里就是整轮报废。

所以之后的处理是把两套名字接起来：`params[].name` 用机器名，`label` 显示中文，`aliases` 接住旧写法。现在 `query` 和 `关键词` 都能进。

**什么时候该用技能**：链长、参数固定、每步不需要临场判断。
**什么时候不该用**：需要看结果再决定下一步的活。我们有一条链是"第一条网页读不了就换第二条"，用 `{"$try": [...]}` 写死了候选顺序——比模型自己判断笨，但快。

## 三、跑一次真实的

```
space_run({ id: "search-and-read", params: { query: "WhaleLife 插件" } })

n1  surf_search   1,026 ms   5 条结果
n2  surf_read     1,104 ms   读到正文
────────────────────────────
合计              2.13 秒    ok
```

**一次工具调用，2.1 秒。** 原生走至少要两轮，光第二轮重传上下文就 2 万 token 起。

再长一点，5 步：

```
surf_search → surf_read(3候选) → surf_search → surf_read(3候选) → surf_status

三次运行   3.4 秒 / 2.4 秒 / 3.4 秒   全部 ok
```

出图链（含模型加载）：

```
comfy_status → comfy_generate   19–25 秒
```

## 四、运行结果分六种，不是两种

这一点我觉得比"能不能跑"更重要：**失败要能分得清。**

| 状态 | 含义 | 该怎么处理 |
|---|---|---|
| `ok` | 成功 | — |
| `failed` | 失败 | 可以重试 |
| `uncertain` | 结果未知（单步超时、信号中断） | **不要自动重试** |
| `blocked` | 缺前置条件：找不到技能、缺必填参数、含副作用未确认 | 补条件再跑 |
| `empty` | 上游没有产出数据 | 后续步骤不该启动 |
| `skipped` | 这一步没跑成，但后面不依赖它 | 继续是安全的 |

**`uncertain` 是其中最需要的一个。** 出图超时、读大文件超时、进程被杀，这时候"重跑"可能多出一张图、多写一次盘。这个状态的意思是"我不知道结果"，不是"失败"。

超时只做了半件事：**它只是不再等，并不强行停掉底层调用**。强行中断比放弃等待更贵，所以宁可留一个诚实的 `uncertain`。

补充一条：**所有步骤都 skipped 时，整体抬成 failed。** 两步全部跳过、一步都没干成，报 `skipped` 会让人误以为没事。

## 五、业务失败：`ok: true` 不等于成功

真事。`comfy_status` 发现服务没启动时，返回的是一句提示文字，不是错误：

```
{ ok: true, data: "ComfyUI 没在跑（8188），用 comfy_start 启动" }
```

执行器把它记成 `ok`，后面那步"出图"照样跑，然后报一串别的错。**链条把"没产出"当成了"产出成功"。**

现在的判断分两档：

```
强词（任意长度，≤300 字）    没在跑 / 未启动 / 已停止 / 显存不够 / 低于阈值 / 超过上限 / 请先启动
弱词（仅 ≤60 字短句）        失败 / 错误 / 无法 / 找不到 / 拒绝 / error / failed / denied
```

**长正文不参与弱词判定**——`surf_read` 读回几千字网页里出现"错误处理"是正常的事。

单测 8 条（正常对象、服务没起、显存不足、短句失败、长正文不误判、结构化结果、空对象、null），8 条通过；端到端两次（服务起着 → ok；真停掉 → n1 就 failed，n2 不启动）。

## 六、自动整理：它自己攒技能

开着 `autoOrganize` 时，插件听宿主的 `tool/called` 事件，记录成 `calls.json`；同一个会话里、间隔小于 `organizeWindowMinutes` 的调用切成 2–5 步的窗口；出现次数过阈值的整理成技能。

**我在实现时踩到的三个坑，可能对别的插件也有用：**

**一、`transientResult: true` 的工具全被丢掉了。**
`surf_search`、`surf_read` 在测试里标了 `transientResult: true`。宿主的语义是"这个工具的结果是临时的、不进历史"，我一开始整个事件都 return 了，结果自动整理**永远看不见读取类工具**，能看到的只剩 `hands_`（危险，跳过）和 `status`（没什么用）。改成"只记工具名、时间、成败，不记参数、不记返回值"就好了。

**二、n-gram 把重复模式展开成了长链。**
连做三轮 `[A, B]`，长度 2、3、4、5 的窗口全部过阈值，于是存出 `A B`、`A B A`、`A B A B` 三条。跑 `A B A B` 等于把两件事干了两遍。
修法是"能由更短的链周期重复拼出来的，丢掉"。**注意判定要检查所有偏移量**——`[A,B,A]` 对 `[A,B]` 从下标 0 对齐判不出来，得看偏移 1。

**三、先截取再过滤，安全链永远轮不上。**
先 `chains.slice(0, 3)` 再判危险，而 `chains` 按出现次数排序——`hands_write → hands_run` 出现 4 次排在前面，三个名额全被需要确认的链占了，安全的链一条都轮不到。改成先过滤、攒够 3 条可用的才停。

**这三条里，第二条和第三条都是"只有真数据撞上才现形"的 bug**，靠单测和我自己造的数据都测不出来。

## 七、自动精简：跑熟了会变短

跑通一次，回头看这条链有没有白跑的步骤。四条全满足才删：

```
一  这一步这次跑成功了
二  它的输出没有被后面任何一步引用
三  它不是最后一步
四  它的工具不需要确认
```

实测（3 步 → 2 步）：

```
n1 ledger_today    ok  494ms   ← 结果没人用
n2 comfy_status    ok  167ms
n3 surf_status     ok   15ms

回执：trimmed { from: 3, to: 2, dropped: [n1], revision: 2 }
```

**有副作用的步骤永远不会被自动删掉**，哪怕结果没人用。

一个坑：第一版一次砍到底，3 步的技能砍成 1 步，`validateSkill` 直接拒绝（复合技能至少 2 步），异常被 catch 吞掉，**表面看什么都没发生**。改成"删到剩 2 步就停手"，并且 catch 里写一行日志。所以 4 步的链会跑一次缩一步，不是一次砍完。

另一件是候选砍枝：`{"$try": [...]}` 连 3 次都是第一条命中，就砍掉后面从没命中的候选（实测 3 个 → 1 个，`revision` 从 1 到 2）。

## 八、想请你定的几条

**一、导航组能不能由插件自己声明？**
「管理」组里的入口，现在是本地改 `core/ui/index.html` 硬加的一行 `<a>`。插件没法说"我要挂在管理组、排在记忆管理上面"。上游一改导航结构这行就得手动跟。如果 `plugin.yaml` 能加个 `navigationGroup: manage`，这类插件就不用改主干了。

**二、插件能不能声明"管理页里不出现"？**
宿主会列出所有已装插件，每个一行，插件没法自己隐藏。这个插件已经在「管理」组有入口了，插件管理里那行是重复的。

**三、`transientResult` 的语义能不能再说清一点？**
我的理解是"结果不进历史/上下文"，但工具名本身不含内容。所以我在记录时保留名字。如果这个理解不对，请指出来。

**四、工具返回失败但 `ok: true`，是约定还是巧合？**
`comfy_status` 返回提示文字、`surf` 有的路径返回 `{status: "error"}` 但宿主仍是 `ok`。我现在两边都做了兜底判断。如果上游有统一的"业务失败"表达方式，我们照它来更省事。

## 九、没验过的

不写这一节就成了吹牛，所以写清楚：

```
一、自动整理在真实使用里长期能不能产出有用的技能      没验
   今天存下的多数来自我的调试操作；真实使用里它只学出过
   "ledger_today → surf_status" 这种，而且它不知道该填什么参数值

二、长链的收益是不是单调的                          没验
   5 步跑通过，但 8 步、10 步没试过。链越长，中间一步废掉代价越大

三、页面视觉                                       没验
   插件作者是模型本身，能验证 HTML 元素存在与否，看不到排版。
   所有页面细节都是人眼看了之后才发现的

四、跨机器                                       没验
   只在本人一台 Windows 电脑上跑过

五、回执的持久化                                  没做
   只在内存留一小时，重启后 space_trace 查不到

六、并发                                         没验
   两条技能同时跑会怎样，不知道
```

还有一处设计上没解决的：**技能之间的编排**。现在一条技能只能调工具，不能调另一条技能。复合功能库那层（技能组技能）还没做。
